## Compatibility and release constraints

New native writes use schema `0.2.0`. The Firestore rules still accept `0.1.0` writes under their original contract (temperature and instrument required, no visual observations or provenance fields) so installed builds are not locked out when the rules deploy; a revision can never change its schema version, and `0.2.0` never falls back to the legacy checks. Retire `0.1.0` in a later rules release once every installed client has updated. Validation treats `0.1.0` records as legacy and does not flag missing visual observations or provenance on them.

Both native clients keep one active draft per account on a device. Save field collection retains the submission, event and revision IDs, persists locally, and synchronizes a mutable private DRAFT when online. Final submission refreshes the current draft contents, removes stale measurement documents while mutable, then freezes the revision before advancing the parent. Submitted revisions cannot be overwritten. Cross-device draft discovery and concurrent mutable draft conflict resolution are not implemented by this slice; do not claim these as verified.

Laboratory completion is an explicit collector action, and each laboratory result records its own analysis method and time. Which field-analysis exceptions are scientifically acceptable is an open supervisor question (docs/SUPERVISOR_QUESTIONS.md row 14); today any documented reason is accepted and surfaced to reviewers. The current shared method/category provenance must not be presented as a verified laboratory protocol. No lab result or required numeric value is invented.
